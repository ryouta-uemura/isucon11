## 1. 計測環境

```
isucon11q        2コア / 3.8GB / 192.168.252.9    アプリ + MariaDB
isucon11q-bench  4コア / 3.8GB / 192.168.252.10   ベンチ専用
```

**ベンチを別VMに分けたのは必須の措置だった。** 同居構成ではベンチ自身が
2コア中 **0.75コア（41.7%）** を消費しており、アプリの性能を測っているつもりで
ベンチとの奪い合いを測っていた。分離後はスコアが 179k → 240k に上がった。

分離にあたりベンチへ2つパッチを当てている（`tools/bench-patch/`）。特に2つ目は必須:

- `patch-tls.py` — `-tls-skip-verify`。アプリVMの自己署名証明書をベンチVMへ配る代わりに検証を切る。
- `patch-tls-poster.py` — **ポスター(`scenario/posting.go`)は `agent.DefaultTLSConfig` を
  使わず自前の Transport を持つ**ため、1つ目だけでは `POST /api/condition` が
  証明書検証で全滅する。症状が「エラーは出ないのに加点だけゼロ」で分かりにくい。

## 2. 作った計測ツール

### レイヤ1: アクセスログの時系列化

nginx を LTSV で吐かせ、**1秒バケット × エンドポイント**に畳んで単一HTMLにする
（`tools/analyze.py`、標準ライブラリのみ + Plotly.js CDN）。
alp/kataribe は全区間の集計しか出さないので「いつ壊れたか」が消える。

log_format の名前は `ltsv` ではなく **`ltsv_ts`** にしてある。競技者側の
`nginx.conf` が既に `log_format ltsv` を定義していることがあり、二重定義は nginx がエラーになるため。

### レイヤ2: スコアの時系列化

ベンチに `-score-dump <path>` を足し、毎秒 JSONL でスコアのスナップショットを出す
（`tools/bench-patch/`）。新しい goroutine は追加せず、既存の3秒ループを1秒に変えて
`sendResult` を3回に1回呼ぶ形にした。**ポータルへの送信頻度は元のまま。**

```json
{"ts":1789746096.91,"raw":12126,"deduction":2,"timeout":27,"score":12124,
 "tags":{"04.GraphWorst":383,"09.ReadInfoCondition":162,...}}
```

`ts` は epoch 秒なので access.log と同じ軸。`POST /initialize` を t=0 として重ねる。
スコア倍率は `bench/scenario/prepare.go` の `Score.Set` と同じ値を持ち、
**最終スナップショットで `sum(count × 倍率) == raw` を検算**して、合わなければ警告を出す。

レポートは8パネル（累積スコア / 秒間加点のタグ別内訳 / 減点 / rps / status / latency /
in-flight / p95ヒートマップ）を x軸共通で縦に並べる。

### 計測オーバーヘッドの検証

`access_log` on/off で nginx は 0.80 vs 0.78 コア（**約2.5%、誤差レベル**）。
ログを出したまま計測して差し支えない。

## 3. ベンチの挙動（読解 + 実測）

### ユーザーが増える条件

`verifyTrend` が返す `newConditionNum`（まだ見ていない、かつ実時間2秒以内の condition の数）が
`viewUpdatedTrendCounter` に積まれ、閾値を超えたときだけユーザーが増える。

**trend が古いと `ConditionAlreadyVerified` で弾かれてカウンタが増えず、ユーザーが増えない。
しかも古いデータを返しても減点されない**（`ConditionIsUpdated` は「より古い timestamp」しか弾かない）。
エラーにならずに上限だけが潰れる。

### コンテスタントに開示されている情報

走行中の `score / raw / deduction / timeout` は **3秒ごとに stdout へ出ている**
（`sendResult` のこの2行は `if finish` の外にある）。`ユーザーは増えませんでした` も出る。
終了時にはタグ別カウントも出るが、`_` 始まり（`ViewerDropout`、`PostCondition` など）は
運営専用で stderr にしか出ない。**ContestantLogger は stdout、AdminLogger は stderr。**

つまり素点の推移だけならパッチなしで取れる。自作 `-score-dump` の価値は
**タグ別内訳の時系列**と `_` 系タグ、そして機械可読性に絞られる。

## 4. 計測結果

### 4.1 素の実装 → ユーザー実装

| | 素の実装 | main ブランチ |
|---|---|---|
| score | 12,802 | 179,034（同居）/ **240,940**（2VM） |
| `GET /api/trend` p50 / p95 | 1001 / 1010 ms | 1 / 7 ms |
| trend の 499 | 94件 (87%) | 0件 |
| `_4.ViewerLoop` | 6 | 11,943 |
| `_5.ViewerDropout` | 21 | 0 |

素の実装は `GET /api/trend` の 108件中94件がベンチの1秒タイムアウトで切断されていた。
5xx は全エンドポイントで0。**落ちているのではなく間に合っていない**状態。

### 4.2 trend キャッシュの鮮度とスコア

現状の実装は `postIsuCondition` 末尾の

```go
err = tx.Commit()
if err != nil { return ... }           // err != nil はここで抜ける
if err != nil && !latestChanged {      // 到達時点で err は必ず nil → 常に false
    invalidateTrendCache()
}
```

により、**コンディション投稿からの invalidate が一度も発火しない**。

| 戦略 | ユーザー増加 | score（同居） | score（2VM） |
|---|---|---|---|
| 凍結（現状） | 0回 | 172,449 | **240,940 / 242,976** |
| TTL 10s | 1回 | 161,017 | — |
| TTL 1s | 12回 | 63,635 | — |
| TTL 500ms | 11回 | 57,272 | — |
| TTL 200ms | 11回 | 53,846 | — |
| `latestChanged` で invalidate | 9〜11回 | 52,619 | **58,878 / 60,486** |

**鮮度を上げるほど単調に下がる。** ベンチ分離後も結論は変わらず、むしろ差が広がった（3.3倍 → 4.1倍）。

理由: ユーザーが増えると ISU が 48→387 に増え、**0点の `POST /api/condition`** が
76k→141k に倍増し、加点対象の読み取り（GraphWorst 13,903→2,206）が押し出される。
総 rps は上がるのにスコアは下がる。

**ただしこれは「アプリVMが2コアで飽和している」という前提の上での結論。**
容量に余裕があればユーザー増加は純粋な上積みになり、逆転しうる。
凍結はスコアを買っているのではなく飽和を隠している。**未検証**。

### 4.3 アプリVMの CPU 内訳（2VM、gzip on）

| プロセス | コア換算 | 占有率 |
|---|---|---|
| **nginx** | **0.79** | 45.1% |
| isucondition | 0.52 | 29.3% |
| mysqld | 0.44 | 25.0% |
| 合計 | 1.75 / 2 コア | |

**最大の消費者は nginx で、DB ではない。** pprof でもアプリの CPU サンプルの上位は
`runtime.epollwait` / `netpoll` / `findrunnable` という待機ばかりで、
アプリコードは `generateIsuGraphResponse` の 1.55% 程度しか出てこない。

`POST /api/condition` は総 request-time の 57.3% を占めるが **1件 2.19ms と軽い**。
「重い」のは回数であって、1件あたりの処理コストではない。

### 4.4 nginx の CPU の正体は gzip

| | gzip on (level 1) | gzip off |
|---|---|---|
| score | 234,058 | **329,315** |
| nginx | 0.79 コア | **0.56 コア** |
| isucondition | 0.52 | 0.60 |
| mysqld | 0.43 | 0.56 |
| 処理リクエスト | 158,837 | 185,701 |
| 送信量 | 40.5 MB (6 Mbps) | 257.7 MB (36 Mbps) |

gzip が **nginx CPU の 0.23 コア（マシン全体の12%）**を食っている。
切ると解放分がアプリと mysqld に回り、処理量が17%増えてスコアが約40%伸びる。

`gzip_comp_level` は既に 1（最小）なので、調整余地は on/off しかない。
帯域は 6→36 Mbps に増えるが、同一ホスト上のVM間では制約にならない。
`notes.txt` の「転送が20%になった」は事実だが、**この環境では帯域を買って CPU を失う取引**。

中間案として `gzip_min_length` を大幅に上げ、trend のような巨大レスポンスだけ圧縮する手はある。

### 4.5 接続構造と HTTP/2

| 指標 | HTTP/2 | HTTP/1.1 |
|---|---|---|
| nginx CPU | 0.78〜0.79 コア | 0.78〜0.79 コア（**差なし**） |
| TCP 接続数 | 1,144〜1,183 | 4,936〜5,155 |
| 接続あたり平均 | 134〜173 | 31 |
| **同時ストリーム数 最大** | **3**（931接続は最大1） | 2 |
| score (n=7 / n=4) | 224〜246k | 204〜254k |

**多重化はほとんど使われていない。** `http2_max_concurrent_streams`（既定128）に対する
利用率は 2.3%。ベンチのエージェントは1ユーザー=1クライアントで**逐次**にリクエストするため、
実態は HTTP/1.1 の keepalive と同じ「接続の使い回し」。並列性はエージェント数から来ている。

それでも **HTTP/2 を外す利点はなかった**。nginx CPU は同じで、接続数が4.3倍になり、
スコアのばらつきが大きくなる（H2 は幅9%、H1 は幅22%）だけだった。

**エンドポイント単位の出し分けは原理的に不可能。** プロトコルは TLS ハンドシェイク中の
ALPN で決まり、リクエストのパスが分かる前に確定している。クライアント単位でやるなら
listen を別ポート/別IPに分けるしかない。

### 4.6 触る価値がなかったもの

- **`ssl_session_cache`**: TLSハンドシェイクは60秒で **1,081回**のみ（全リクエストの0.68%、
  接続あたり平均147リクエスト）。1回1msと置いても nginx CPU の約3%。
  keepalive が既に効いているのでセッションキャッシュの出番がない。
- **`keepalive_requests` / `http2_max_requests`**: 1000本に到達して打ち切られた接続は
  1,154本中 **136本（11.8%）**のみ。上げても削れるのは1%未満。
- **TLSのバルク暗号**: gzip off で6倍のバイトを暗号化しても nginx CPU は**減る**。
  AES-NI があるのでバルク暗号は実質タダ。「TLSが重い」の重さはハンドシェイク側にある。

なお `upstream` の `keepalive 256`（nginx→アプリ）は別物で、これは効いている。

## 5. 実装側で見つかった弱点

1. **`GET /api/isu/:uuid/icon` が誤ったステータスを返す。**
   `期待する HTTP ステータスコード以外が返却されました (expected: 401,404,304): 200`。
   deduction 11〜33 の原因。`X-Accel-Redirect` 化のときに認可と 304 判定が抜けたと思われる。
   **減点をゼロにできる確実な一手。**
2. **`jiaURL` がグローバル変数で起動時に1度しか読まれない**（`main.go` 443行目）。
   `postInitialize` が DB を更新してもリフレッシュされないため、JIA の URL を変えたら
   アプリの再起動が必要。本番でも URL が変わると事故る。
3. **trend キャッシュの invalidate が死んでいる**（4.2 参照）。
   現状は有利に働いているが、意図した動作ではない。
4. **高倍率のスコアタグが全て 0**。`GraphGood`(150点) `GraphNormal`(100点)
   `TodayGraphGood`(60点) が一度も入らず、加点の79%が最安の `GraphWorst`(10点)。
   素の実装でも同傾向なので**実装起因かは切り分けできていない**。

## 6. 途中で誤っていた判断（記録として）

同じ轍を踏まないための記録。

- **「`ssl_session_cache` と `keepalive_requests` が効く」** → 実測すると合わせて nginx CPU の5%未満。
  ハンドシェイク回数を数えずに一般論で挙げたのが誤り。
- **「CPU飽和はアプリの限界」** → 同居構成ではベンチが0.75コアを食っていた。
  プロセス別に分解せず、システム全体の使用率だけ見ていたのが誤り。
- **「slow query log が効いている」** → OFF にしても差は走行間のばらつきの範囲だった。
- **「多重化していないなら h2 は純損」** → nginx CPU に差は出なかった。
- **6.7秒の停止を SYN 再送と推定** → `$request_time` はハンドシェイクを含まないので的外れ。
  実際は `apptime` 21〜33ms でアプリは即答しており、詰まったのは応答書き出し側。
  `ListenOverflows`/`ListenDrops` も0。**原因未特定**（ベンチ側の一時停止が疑わしいが n=1）。

**共通する失敗は「数えずに語ったこと」。** 1回の走行は1.5分で終わるので、
仮説は測ってから述べる方が速い。
