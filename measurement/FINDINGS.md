## 1. 計測環境

> **注**: この章は最初期（アプリVM 2コア + DB同居）の構成。
> 途中で**4コア×2台（app+bench / DB専用）**に組み替えている（4.7 以降）。
> 3章以降の数値は、どの構成で測ったものかを各節で明記している。


```
isucon11q        2コア / 3.8GB / 192.168.252.9    アプリ + MariaDB
isucon11q-bench  4コア / 3.8GB / 192.168.252.10   ベンチ専用
```

**ベンチを別VMに分けたのは必須の措置だった。** 同居構成ではベンチ自身が
2コア中 **0.75コア（41.7%）** を消費しており、アプリの性能を測っているつもりで
ベンチとの奪い合いを測っていた。分離後はスコアが 179k → 240k に上がった。

分離にあたりベンチへ2つパッチを当てている（`tools/bench-patch/`）。特に2つ目は必須:

- `patch-tls.py` — `-tls-skip-verify`。アプリVMの自己署名証明書をベンチVMへ配る代わりに検証を切る。
- `patch-tls-poster.py` — **ポスター(`scenario/posting.go`)は `agent.DefaultTLSConfig` を
  使わず自前の Transport を持つ**ため、1つ目だけでは `POST /api/condition` が
  証明書検証で全滅する。症状が「エラーは出ないのに加点だけゼロ」で分かりにくい。

## 2. 作った計測ツール

### レイヤ1: アクセスログの時系列化

nginx を LTSV で吐かせ、**1秒バケット × エンドポイント**に畳んで単一HTMLにする
（`tools/analyze.py`、標準ライブラリのみ + Plotly.js CDN）。
alp/kataribe は全区間の集計しか出さないので「いつ壊れたか」が消える。

log_format の名前は `ltsv` ではなく **`ltsv_ts`** にしてある。競技者側の
`nginx.conf` が既に `log_format ltsv` を定義していることがあり、二重定義は nginx がエラーになるため。

### レイヤ2: スコアの時系列化

ベンチに `-score-dump <path>` を足し、毎秒 JSONL でスコアのスナップショットを出す
（`tools/bench-patch/`）。新しい goroutine は追加せず、既存の3秒ループを1秒に変えて
`sendResult` を3回に1回呼ぶ形にした。**ポータルへの送信頻度は元のまま。**

```json
{"ts":1789746096.91,"raw":12126,"deduction":2,"timeout":27,"score":12124,
 "tags":{"04.GraphWorst":383,"09.ReadInfoCondition":162,...}}
```

`ts` は epoch 秒なので access.log と同じ軸。`POST /initialize` を t=0 として重ねる。
スコア倍率は `bench/scenario/prepare.go` の `Score.Set` と同じ値を持ち、
**最終スナップショットで `sum(count × 倍率) == raw` を検算**して、合わなければ警告を出す。

レポートは8パネル（累積スコア / 秒間加点のタグ別内訳 / 減点 / rps / status / latency /
in-flight / p95ヒートマップ）を x軸共通で縦に並べる。

### 計測オーバーヘッドの検証

`access_log` on/off で nginx は 0.80 vs 0.78 コア（**約2.5%、誤差レベル**）。
ログを出したまま計測して差し支えない。

## 3. ベンチの挙動（読解 + 実測）

### ユーザーが増える条件

`verifyTrend` が返す `newConditionNum`（まだ見ていない、かつ実時間2秒以内の condition の数）が
`viewUpdatedTrendCounter` に積まれ、閾値を超えたときだけユーザーが増える。

**trend が古いと `ConditionAlreadyVerified` で弾かれてカウンタが増えず、ユーザーが増えない。
しかも古いデータを返しても減点されない**（`ConditionIsUpdated` は「より古い timestamp」しか弾かない）。
エラーにならずに上限だけが潰れる。

### コンテスタントに開示されている情報

走行中の `score / raw / deduction / timeout` は **3秒ごとに stdout へ出ている**
（`sendResult` のこの2行は `if finish` の外にある）。`ユーザーは増えませんでした` も出る。
終了時にはタグ別カウントも出るが、`_` 始まり（`ViewerDropout`、`PostCondition` など）は
運営専用で stderr にしか出ない。**ContestantLogger は stdout、AdminLogger は stderr。**

つまり素点の推移だけならパッチなしで取れる。自作 `-score-dump` の価値は
**タグ別内訳の時系列**と `_` 系タグ、そして機械可読性に絞られる。

## 4. 計測結果

### 4.1 素の実装 → ユーザー実装

| | 素の実装 | main ブランチ |
|---|---|---|
| score | 12,802 | 179,034（同居）/ **240,940**（2VM） |
| `GET /api/trend` p50 / p95 | 1001 / 1010 ms | 1 / 7 ms |
| trend の 499 | 94件 (87%) | 0件 |
| `_4.ViewerLoop` | 6 | 11,943 |
| `_5.ViewerDropout` | 21 | 0 |

素の実装は `GET /api/trend` の 108件中94件がベンチの1秒タイムアウトで切断されていた。
5xx は全エンドポイントで0。**落ちているのではなく間に合っていない**状態。

### 4.2 trend キャッシュの鮮度とスコア

現状の実装は `postIsuCondition` 末尾の

```go
err = tx.Commit()
if err != nil { return ... }           // err != nil はここで抜ける
if err != nil && !latestChanged {      // 到達時点で err は必ず nil → 常に false
    invalidateTrendCache()
}
```

により、**コンディション投稿からの invalidate が一度も発火しない**。

| 戦略 | ユーザー増加 | score（同居） | score（2VM） |
|---|---|---|---|
| 凍結（現状） | 0回 | 172,449 | **240,940 / 242,976** |
| TTL 10s | 1回 | 161,017 | — |
| TTL 1s | 12回 | 63,635 | — |
| TTL 500ms | 11回 | 57,272 | — |
| TTL 200ms | 11回 | 53,846 | — |
| `latestChanged` で invalidate | 9〜11回 | 52,619 | **58,878 / 60,486** |

**鮮度を上げるほど単調に下がる。** ベンチ分離後も結論は変わらず、むしろ差が広がった（3.3倍 → 4.1倍）。

理由: ユーザーが増えると ISU が 48→387 に増え、**0点の `POST /api/condition`** が
76k→141k に倍増し、加点対象の読み取り（GraphWorst 13,903→2,206）が押し出される。
総 rps は上がるのにスコアは下がる。

**ただしこれは「アプリVMが2コアで飽和している」という前提の上での結論。**
容量に余裕があればユーザー増加は純粋な上積みになり、逆転しうる。
凍結はスコアを買っているのではなく飽和を隠している。**未検証**。

### 4.3 アプリVMの CPU 内訳（2VM、gzip on）

| プロセス | コア換算 | 占有率 |
|---|---|---|
| **nginx** | **0.79** | 45.1% |
| isucondition | 0.52 | 29.3% |
| mysqld | 0.44 | 25.0% |
| 合計 | 1.75 / 2 コア | |

**最大の消費者は nginx で、DB ではない。** pprof でもアプリの CPU サンプルの上位は
`runtime.epollwait` / `netpoll` / `findrunnable` という待機ばかりで、
アプリコードは `generateIsuGraphResponse` の 1.55% 程度しか出てこない。

`POST /api/condition` は総 request-time の 57.3% を占めるが **1件 2.19ms と軽い**。
「重い」のは回数であって、1件あたりの処理コストではない。

### 4.4 nginx の CPU の正体は gzip

| | gzip on (level 1) | gzip off |
|---|---|---|
| score | 234,058 | **329,315** |
| nginx | 0.79 コア | **0.56 コア** |
| isucondition | 0.52 | 0.60 |
| mysqld | 0.43 | 0.56 |
| 処理リクエスト | 158,837 | 185,701 |
| 送信量 | 40.5 MB (6 Mbps) | 257.7 MB (36 Mbps) |

gzip が **nginx CPU の 0.23 コア（マシン全体の12%）**を食っている。
切ると解放分がアプリと mysqld に回り、処理量が17%増えてスコアが約40%伸びる。

`gzip_comp_level` は既に 1（最小）なので、調整余地は on/off しかない。
帯域は 6→36 Mbps に増えるが、同一ホスト上のVM間では制約にならない。
`notes.txt` の「転送が20%になった」は事実だが、**この環境では帯域を買って CPU を失う取引**。

中間案として `gzip_min_length` を大幅に上げ、trend のような巨大レスポンスだけ圧縮する手はある。

### 4.5 接続構造と HTTP/2

| 指標 | HTTP/2 | HTTP/1.1 |
|---|---|---|
| nginx CPU | 0.78〜0.79 コア | 0.78〜0.79 コア（**差なし**） |
| TCP 接続数 | 1,144〜1,183 | 4,936〜5,155 |
| 接続あたり平均 | 134〜173 | 31 |
| **同時ストリーム数 最大** | **3**（931接続は最大1） | 2 |
| score (n=7 / n=4) | 224〜246k | 204〜254k |

**多重化はほとんど使われていない。** `http2_max_concurrent_streams`（既定128）に対する
利用率は 2.3%。ベンチのエージェントは1ユーザー=1クライアントで**逐次**にリクエストするため、
実態は HTTP/1.1 の keepalive と同じ「接続の使い回し」。並列性はエージェント数から来ている。

それでも **HTTP/2 を外す利点はなかった**。nginx CPU は同じで、接続数が4.3倍になり、
スコアのばらつきが大きくなる（H2 は幅9%、H1 は幅22%）だけだった。

**エンドポイント単位の出し分けは原理的に不可能。** プロトコルは TLS ハンドシェイク中の
ALPN で決まり、リクエストのパスが分かる前に確定している。クライアント単位でやるなら
listen を別ポート/別IPに分けるしかない。

### 4.6 触る価値がなかったもの

- **`ssl_session_cache`**: TLSハンドシェイクは60秒で **1,081回**のみ（全リクエストの0.68%、
  接続あたり平均147リクエスト）。1回1msと置いても nginx CPU の約3%。
  keepalive が既に効いているのでセッションキャッシュの出番がない。
- **`keepalive_requests` / `http2_max_requests`**: 1000本に到達して打ち切られた接続は
  1,154本中 **136本（11.8%）**のみ。上げても削れるのは1%未満。
- **TLSのバルク暗号**: gzip off で6倍のバイトを暗号化しても nginx CPU は**減る**。
  AES-NI があるのでバルク暗号は実質タダ。「TLSが重い」の重さはハンドシェイク側にある。

なお `upstream` の `keepalive 256`（nginx→アプリ）は別物で、これは効いている。

ここから先は**ユーザーの 130万点構成を再現した環境**での測定。前節までとは前提が違う。

| VM | スペック | 役割 |
|---|---|---|
| `isucon11q` | 4コア / 4GB | nginx + app（+ ベンチ同居の測定もあり） |
| `isucon11q-db` | 4コア / 4GB | MariaDB 専用 |
| `isucon11q-bench` | 3コア | ベンチ専用 |

**ホストは12コア。VM合計を12に張ると macOS ごと飽和する**（load average 11.62 を実測）。
一度それでベンチVMがCPU不足になり、`GET /api/isu/:uuid/graph` が 7,070→2,883 に半減して
スコアが 392k に落ちた。**構成の優劣ではなく測定の失敗**。

### 4.8 グラフのスコア機構（最も重要）

`bench/scenario/load.go`:
```go
minTimestampCount = 全時間ブロックの min(len(g.ConditionTimestamps))
if minTimestampCount > 20 { return ScoreGraphGood }    // 150点
if minTimestampCount > 10 { return ScoreGraphNormal }  // 100点
if minTimestampCount >  5 { return ScoreGraphBad }     //  60点
return ScoreGraphWorst                                 //  10点
```

**1時間ブロックに 20 件を超えるコンディションが入っていないと Good にならない。
しかも全ブロックの最小値**なので、1つでも薄いブロックがあると全体が引きずられる。

時間スケール（`virtualTimeMulti = 30000`）:
- 1実秒 = 8.3仮想時間
- **グラフの1時間ブロック = 実時間 120ms**
- 1仮想日 = 実時間 2.88秒

投稿レートは `PostIntervalSecond = 60`（仮想60秒に1件）なので、1ブロックの上限は **60件**。
ベンチのソースにも `// MEMO: 最大でも60秒に一件しか送れないので点数上限になる` とある。

### 4.9 dropProbability

`try-current-app-2vm` ブランチには初期実装由来の `dropProbability := 0.9` が残っていた。

| 変種 | score | Good(150) | Worst(10) | mysqld |
|---|---|---|---|---|
| `0.9`（ブランチ現状） | 268,042 / 286,293 | 0 | 21,947 | 1.33 コア |
| `0.0`（rand は呼ぶ） | 1,049,567 / 982,410 | — | — | — |
| ロジックごと削除 | 1,315,567 / 943,326 | 3,834 | 687 | 2.45 コア |

**90%捨てるとブロックが薄くなって全部 Worst(10点)、全部保存すると Good(150点) に化ける。15倍。**

`math/rand` のコストは測定できない（アプリCPU 1.06 vs 1.07 コア、
`POST /api/condition` の p50 9ms で同一）。効いているのは「捨てないこと」だけ。

**中間の drop は成立しない**:

| drop | score | Good | Normal | Bad | Worst | mysqld |
|---|---|---|---|---|---|---|
| 0.0 | 462,567 | **746** | 815 | 82 | 233 | 2.57 コア |
| 0.3 | 330,691 | **0** | 103 | 1,802 | 2,198 | 2.40 コア |
| 0.5 | 221,076 | **0** | 0 | 243 | 7,255 | 2.20 コア |

0.3 で既に Good が全滅する。最小値で決まるうえ、ISU作成直後や進行中の半端なブロックが
必ず混ざるため。**drop 0 でも Good 746 に対し Normal 815 と拮抗しており、素で既にギリギリ。**
DBの節約も 14% しかなく（読み取りクエリが支配的なため）、割に合わない。

### 4.10 律速はCPUではなくレイテンシ

ベンチの通常ユーザーは逐次リクエストなので、ループ1周 = 各レイテンシの合計。

| endpoint | 件数 | 消費秒 | 占有 | 1件 | スコア寄与 |
|---|---|---|---|---|---|
| `GET /api/condition/:uuid` | 40,195 | 185.9 | **57.1%** | 4.62ms | 約237k (25%) |
| `GET /api/isu/:uuid/graph` | 7,070 | 79.1 | **24.3%** | 11.19ms | 約604k (65%) |
| `GET /api/isu` | 5,353 | 23.7 | 7.3% | 4.43ms | **0点** |
| `GET /api/isu/:uuid` | 5,503 | 22.3 | 6.8% | 4.05ms | **0点** |
| 合計 | | **325.7秒** | (462ユーザー秒中70%) | | |

点効率は graph **7,636 点/秒** vs condition **1,275 点/秒**。ただし**ループは固定順序なので
どこを速くしても全周が縮み、全部が増える**。0点の `GET /api/isu` 系（計14%）も同じだけ効く。

**上限の見積もり**: 応答待ち 325.7秒 / クライアント側処理 136秒。
応答を半分にすれば 1.55倍、ゼロにしても **3.4倍が理論限界**。
7ユーザーのままでも150万は射程内、300万超えはユーザー増加なしでは不可能。

### 4.11 SQL の内訳と、接続 churn の発見

slow query log（`long_query_time=0`）、総175.4秒:

| 占有 | 回数 | 平均 | 調査行/回 | クエリ |
|---|---|---|---|---|
| **61.1%** | 75,113 | 1.427ms | - | INSERT INTO isu_condition |
| 17.6% | 75,113 | 0.412ms | 1.0 | UPDATE latest_isu_condition |
| 11.9% | 37,334 | **0.561ms** | 35.6 | SELECT condition |
| 8.1% | 3,803 | **3.743ms** | **648.9** | SELECT graph |

**condition の SELECT は 0.561ms しかない**＝エンドポイント4.62msの12%。
残り約4msはアプリ/ネットワーク側。ここから追って **`SetMaxIdleConns` 未設定**に行き着いた。

```go
db.SetMaxOpenConns(20)   // あった
// SetMaxIdleConns が無い → Go の既定値は 2
```

MaxIdle < MaxOpen だとクエリ完了時にアイドル上限を超えた接続が破棄され、
次のクエリで再接続する。DBが別ホストなので1接続あたり約2ms。

| | 修正前 | 修正後 |
|---|---|---|
| score | 513,715 / 581,668 / 600,183 | **1,187,732 / 1,203,492 / 1,230,016 / 1,497,256** |
| 1走行の新規接続数 | **40,224** | **21** |
| `GET /api/condition` p50 | 4.0ms | **2.0ms** |
| `GET /api/isu/:uuid/graph` p50 | 10ms | **7ms** |

プールサイズ自体（20/50/100）は差が走行間の変動に埋もれる。効くのは
**「MaxIdle >= MaxOpen」という関係だけ**。`MaxOpenConns` は据え置いた。

**この見つけ方は再利用できる**:
1. エンドポイントのレイテンシ内訳を取る
2. slow query log で SQL の実測時間と突き合わせる
3. 差が大きければ pprof（`runtime.futex` / `syscall` が上位なら待ち）
4. `SHOW GLOBAL STATUS LIKE 'Connections'` で接続 churn を確認

**残るSQL改善余地**: graph の SELECT（3.743ms / 648.9行）が単体で最重。
condition 側の `level_int` インデックス追加は無駄（**リクエストの90%が
`condition_level=info,warning,critical` の全レベル指定**で、フィルタにならない）。

### 4.12 3台構成とユーザー増加

ベンチを別VMに出した有効な測定では、**どこも飽和していない**
（app 2.57/4=64%、DB 2.56/4=64%、bench 1.73/3=58%、ホスト load 9.79/12）。
この負荷レベルでは3台目に仕事がない。

ユーザー増加（trendキャッシュの invalidate）は、**飽和していない状態でも負ける**
（285,754 vs 凍結時 541,670）。drop削除後・DB分離後でも同じ（約100万 vs 36万）。

### 4.13 接続 churn（この日で最大の発見）

`GET /api/condition/:uuid` がループの57%を占めていたので slow query log で SQL を測ったところ、
**そのSELECTは 0.561ms しかなかった**（エンドポイントは4.62ms）。SQLは12%で、残りはどこか別。
pprof を見ると `runtime.futex` 24% / `syscall` 20% と、計算ではなく待ちが支配的。
`SHOW GLOBAL STATUS LIKE 'Connections'` が **577,255** で接続 churn を特定した。

```go
db.SetMaxOpenConns(20)   // あった
// SetMaxIdleConns が無い → Go の既定値は 2
```

MaxIdle < MaxOpen だと、クエリ完了時にアイドル上限を超えた接続が破棄され、
次のクエリで再接続する。DB が別ホストなので1接続あたり
TCP handshake + MySQL 認証で約2ms。

| | 修正前 | 修正後 |
|---|---|---|
| 1走行の新規接続数 | **40,224** | **21** |
| `GET /api/condition` p50 | 4.0ms | **2.0ms** |
| `GET /api/isu/:uuid/graph` p50 | 10ms | **7ms** |
| score（ベンチ別VM） | 513,715 / 581,668 / 600,183 | 1,187,732 / 1,203,492 / 1,497,256 |
| score（ベンチ同居） | 943,326 / 1,315,567 | **2,048,251 / 1,985,396** |

プールサイズ自体（20/50/100/150）は差が走行間の変動に埋もれる。
効くのは **「MaxIdle >= MaxOpen」という関係だけ**。

**この見つけ方は再利用できる**:
1. エンドポイントのレイテンシ内訳を取る
2. slow query log で SQL の実測時間と突き合わせる
3. 差が大きければ pprof（`runtime.futex` / `syscall` が上位なら待ち）
4. `SHOW GLOBAL STATUS LIKE 'Connections'` で接続 churn を確認

### 4.14 確定した日のグラフのメモ化

`GET /api/isu/:uuid/graph` 14,388件に対し、ユニークな (ISU, 日) は **1,249件だけ**
（平均11.5回、最大90回の重複要求）。さらに **95.3% が「もう変わらない過去の日」**で、
graph の消費時間の97%、ユーザーループ全体の42%を占めていた。
1仮想日 = 実時間2.88秒と日付が猛烈に進むため、読まれるのはほぼ過去日になる。

**バッチも事前集計テーブルも不要**。要求が来たら作って覚えるだけ（lazy memoization）で足りる。
JSONバイト列で持てばシリアライズも省ける。

**肝**: 「その日が確定したか」の判定に**アプリの壁時計は使えない**。timestamp は仮想時間なので、
**受信した condition の最大 timestamp** を仮想時刻の代理にする。
margin 3600秒は、ポスターが `PostContentNum(10) × PostIntervalSecond(60) = 600仮想秒`
さかのぼった timestamp も送ってくる分。

結果: `GET /api/isu/:uuid/graph` **8.63ms → 0.84ms**（要求数は 14,388 → 32,481 に増加）。
ループのサーバ待ちは 287.7秒 → 197.8秒。score 2,048,251 → 3,920,958。
**ベンチの検証エラーはゼロ**。

### 4.15 収穫逓減に到達

さらに `GET /api/isu/:uuid`（SQL 0.040ms なのに 1.68ms だった。往復が効いていた）と
`GET /api/isu`（isu LEFT JOIN latest_isu_condition）を in-memory 化した。

| | エンドポイント | score |
|---|---|---|
| `GET /api/isu/:uuid` | 1.68ms → **0.66ms** | 約3.9M → 4.12〜4.65M |
| `GET /api/isu` | 1.90ms → **0.70ms** | **横ばい**（3.99〜4.21M） |

**最後の一手はエンドポイントが2.7倍速くなったのにスコアが動かなかった。**
この時点で 462ユーザー秒の内訳が
**サーバ待ち 178秒(39%) / ベンチ側処理 284秒(61%)** になっており、後者は触れない。
16.8秒削っても周回数は約4%増にとどまり、走行間変動（±15%）に埋もれる。

残る最大項 `GET /api/condition/:uuid`（ループの56%）はキャッシュ不可
（47,718件中ユニーク44,592件、平均1.07回。end_time を変えながらページングするため）。
仮に完全にゼロにしても `462/284 = 1.63倍` が理論上限。

## 5. 実装側で見つかった弱点

1. **`GET /api/isu/:uuid/icon` が誤ったステータスを返す。**（未修正）
   `期待する HTTP ステータスコード以外が返却されました (expected: 401,404,304): 200`。
   最後まで残った唯一の減点源（1走行で7件前後）。`X-Accel-Redirect` 化のときに
   認可と 304 判定が抜けたと思われる。**減点をゼロにできる確実な一手。**
2. **`jiaURL` がグローバル変数で起動時に1度しか読まれない。**（未修正、`main.go` 443行目）
   `postInitialize` が DB を更新してもリフレッシュされないため、JIA の URL を変えたら
   **アプリの再起動が必要**。作業中に2回踏んだ。本番でも URL が変わると事故る。
3. **`bin/run.sh`（2vmブランチ）のバグ。** `cp nginx/*.params` は実ファイル名
   `proxy_params` / `scgi_params` / `uwsgi_params`（アンダースコア）にマッチせず、
   `set -e` で中断する。正しくは `nginx/*_params`。
4. **trend キャッシュの invalidate が死んでいる**（4.2 参照）。
   `tx.Commit()` のエラー時に return 済みなので、後続の `err != nil` が常に false。
   現状は有利に働いているが、意図した動作ではない。
5. **高倍率のスコアタグを取りこぼしている。** `dropProbability` 削除後は
   `01.GraphGood` が主役になったが、`02.GraphNormal`(100点) や `04.GraphWorst`(10点) も残る。
   全部 Good にできれば +10%程度。薄いブロックの特定が要る。

## 6. 途中で誤っていた判断（記録として）

同じ轍を踏まないための記録。この日、**9回外した**。

- **「`ssl_session_cache` と `keepalive_requests` が効く」** → 合わせて nginx CPU の5%未満。

  システム全体の使用率だけ見てプロセス別に分解していなかった。
- **「slow query log が効いている」** → OFF にしても差は走行間のばらつきの範囲。
- **「多重化していないなら h2 は純損」** → nginx CPU に差は出なかった。
- **6.7秒の停止を SYN 再送と推定** → `$request_time` はハンドシェイクを含まないので的外れ。
- **「ベンチ配置でスコア構成が変わった」** → 違う variant（drop有/無）同士を比較したミス。

## 7. 計測の罠

- **VMの時刻がずれると `POST /api/auth` が 403 になり全滅する。**
  ベンチの JWT の `iat` が未来に見えて検証に失敗する。負荷でアプリVMが2分遅れた。
  **スコア0の走行を見たらまず3台で `date` を比べる。**
  `sudo systemctl restart systemd-timesyncd` で復旧。
- **ベンチを同居させるとベンチ自身がCPUを食う**（2コア機で0.75コア = 42%）。
- **multipass のVM合計コア数をホストの物理コア数まで張ると、ホストごと飽和する。**
  一度これでベンチが負荷を出し切れず、スコアが構成の違いに見えた（実際は測定の失敗）。
- **走行ごとに access.log をローテートすること。** 混ざると転送量や件数の集計が壊れる。
- **この水準ではスコアの走行間変動が大きい**（同一設定で 943k〜1,316k など、±15〜30%）。
  単発の走行で比較しない。数%の差は解決できない。
- **ビルド失敗を握りつぶさないこと。** `go build ... | head -5 && echo BUILD_OK` は
  失敗しても OK を出す。3走行を無駄にした。
