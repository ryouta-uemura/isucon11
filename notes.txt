# 2026-09-19 計測メモ

構成: app+nginx+bench 同居(4vCPU) / DB専用(4vCPU)。詳細は measurement-tooling ブランチの
measurement/FINDINGS.md に、計測ツールは measurement/tools/ に置いた。

## スコアの正体

グラフの配点は「1時間ブロックに入っているコンディション数」で決まる。
bench/scenario/load.go:

    minTimestampCount = 全時間ブロックの min(len(g.ConditionTimestamps))
    > 20 なら GraphGood(150点) / > 10 で Normal(100) / > 5 で Bad(60) / それ以下は Worst(10)

最小値なので1つでも薄いブロックがあると全体が引きずられる。
virtualTimeMulti=30000 なので 1時間ブロック = 実時間 120ms、1仮想日 = 2.88秒。
PostIntervalSecond=60 より 1ブロックの上限は 60件。

dropProbability を消すと全部 Worst(10) から Good(150) に化けるのはこれが理由。15倍。
中間値(0.3)は成立しない。最小値で決まる上、半端なブロックが必ず混ざるので Good が全滅する。
DBの節約も14%しかない(読み取りクエリが支配的なため)。

## 効いた施策

1. db.SetMaxIdleConns  … score 約2倍
   SetMaxOpenConns(20) だけあって SetMaxIdleConns が無く、Goの既定値2が効いていた。
   クエリ毎に接続が破棄され、1走行で 40,224 回も再接続していた(修正後は21回)。
   DBが別ホストなので1接続あたり TCP handshake + MySQL認証で約2ms。
   プールサイズ自体(20/50/100)は差が出ない。効くのは MaxIdle >= MaxOpen という関係。

2. 確定した日のグラフのメモ化 … さらに約2倍
   graph 14,388件に対しユニークな(ISU,日)は1,249件だけ。平均11.5回、最大90回の重複要求。
   しかも95.3%が「もう変わらない過去の日」。8.63ms -> 0.84ms。

   確定判定にアプリの壁時計は使えない(timestampは仮想時間)。受信した condition の
   最大 timestamp を仮想時刻の代理にする。margin 3600秒はポスターが
   PostContentNum(10) x PostIntervalSecond(60) = 600仮想秒 さかのぼって送ってくる分。

   1,315,567 -> 2,048,251 (1) -> 3,920,958 (2)

## 測って「やらなくてよい」と分かったもの

- 3台目の追加: ベンチを別VMに出すと app 64% / DB 64% で、どこも飽和していない
- INSERT の queuing: DB は飽和しておらず、書き込みはDB負荷の支配項でもない
  (drop 0.5 で書き込みを半減させても mysqld は 2.57 -> 2.20 コアにしかならない)
- ssl_session_cache / keepalive_requests: TLSハンドシェイクは60秒で1,081回のみ、
  接続あたり平均147リクエスト。nginx CPU の5%未満
- HTTP/1.1化: nginx CPU は変わらず、接続数が4.3倍になって不安定化するだけ
  (同時ストリーム数は最大3で、そもそも多重化をほとんど使っていない)
- trendキャッシュの invalidate: どの構成でも凍結が優位。飽和していなくても負ける
- level_int のインデックス追加: リクエストの90%が condition_level=info,warning,critical の
  全レベル指定で、フィルタにならない。既存の idx (jia_isu_uuid, timestamp) が最適
- MaxOpenConns を増やす: 20/50/100 で差が走行間の変動に埋もれる

## 残っている改善余地

ユーザーループの時間内訳(メモ化後、7ユーザー x 66秒 = 462ユーザー秒中 197.8秒 = 43%):

    GET /api/condition/:uuid  47,718件  105.9秒  53.5%  2.22ms
    GET /api/isu/:uuid/graph  32,481件   27.2秒  13.8%  0.84ms
    GET /api/isu              12,925件   26.7秒  13.5%  2.06ms  <- 0点
    GET /api/isu/:uuid        13,077件   22.0秒  11.1%  1.68ms  <- 0点

ベンチの通常ユーザーは逐次リクエストなので、ループ1周 = 各レイテンシの合計。
どこを速くしても全周が縮んで全部増えるので、0点のエンドポイントを削るのも同じだけ効く。
サーバ待ちが43%まで下がったので、全部ゼロにしても残りは1.75倍が上限。

未修正: GET /api/isu/:uuid/icon が 401/404/304 を返すべき場面で 200 を返す(減点の原因)。

## 計測の罠

- VMの時刻がずれると POST /api/auth が 403 になり全滅する(JWTのiatが未来に見える)。
  スコア0の走行を見たらまず date を3台で比べる。systemd-timesyncd の再起動で直る。
- ベンチを同居させるとベンチ自身が2コア中0.75コアを食う。
- multipassのVM合計コア数をホストの物理コア数まで張ると、ホストごと飽和して
  ベンチが負荷を出し切れなくなる。
- この水準ではスコアの走行間変動が大きい(同一設定で943k〜1,316kなど)。単発で比較しない。
